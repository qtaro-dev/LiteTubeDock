# LiteTubeDock v0.2.1 コードレビュー結果

## レビュー対象

- 対象リポジトリ: https://github.com/qtaro-dev/LiteTubeDock
- 対象バージョン: `v0.2.1` 相当
- レビュー実施日: 2026-06-15
- 確認対象: 現在のワークツリー上の実装

## 総評

ビルドは Debug / Release ともに警告0・エラー0で成功しました。ただし、今回の変更範囲で重要な IPC と WebView2 JavaScript 連携に、実利用で誤成功・誤操作につながる問題が残っています。

特に `UnifiedPlayerControlService` は、JavaScript側の操作結果を「要求を投げた」段階で成功扱いにしている箇所があり、シーク不可、範囲外、再生拒否、必須パラメータ欠落を正しく失敗として返せません。LiteTubeDockControl から見た場合、成功レスポンスなのに実際のプレイヤー状態が変わっていない、または意図しない音量/ミュート状態へ変わるリスクがあります。

## 指摘詳細

### 1. High: `player-set-volume` / `player-set-muted` の必須パラメータ欠落が成功扱いになる

- 対象ファイル: `Services/IpcCommandHandler.cs`
- 対象行: 538-559, 680-730
- 関連ファイル: `Services/UnifiedPlayerControlService.cs`
- 関連行: 565-572, 596-609
- 問題内容:
  - 旧IPCの `set-volume` / `set-muted` は `TryReadVolumePercent` / `TryReadMuted` で必須値を検証しています。
  - 一方、新IPCの `player-set-volume` / `player-set-muted` は、値が存在する場合だけ型・範囲を検証し、未指定の場合はエラーにしません。
  - その後 `PlayerControlFromIpcOnUiAsync` では未指定値を `null` のまま JS に渡します。
  - JS側では `player-set-volume` 相当の操作で `state.desiredVolumePercent = clampPercent(requestedVolumePercent)` が `null` になり、続く `target.volume = state.desiredVolumePercent / 100` により `null / 100 == 0` として音量0%が適用されます。
  - `player-set-muted` では `Boolean(requestedMuted)` により、未指定が `false` として扱われ、ミュート解除になります。
  - `volume-mismatch` / `muted-set` は失敗条件に含まれていないため、IPCレスポンスは成功になります。
- 発生条件:
  - LiteTubeDockControl などから `{"command":"player-set-volume"}` のように `volumePercent` なしで送信する。
  - または `{"command":"player-set-muted"}` のように `muted` なしで送信する。
- 想定される影響:
  - 不正なIPCなのに成功レスポンスが返る。
  - 音量が意図せず0%になる。
  - ミュート状態が意図せず解除される。
  - Control側の状態表示と実プレイヤー状態がずれる。
- 修正案:
  - `ControlPlayerAsync` で `player-set-volume` は `volumePercent` 必須、`player-set-muted` は `muted` 必須として、旧IPCと同じ検証を行う。
  - JS側でも `set-volume` は `requestedVolumePercent === null`、`set-muted` は `requestedMuted === null` を `invalid-parameter` として失敗にする。
  - `volume-mismatch` / `muted-mismatch` も失敗条件に含める。
- 修正要否:
  - 必須修正です。

### 2. High: `player-seek` / `seek-to` が seekable 範囲・動画長・実位置を検証せず成功扱いになる

- 対象ファイル: `Services/UnifiedPlayerControlService.cs`
- 対象行: 557-564, 596-609
- 関連ファイル: `MainWindow.xaml.cs`
- 関連行: 689-711, 893-916
- 問題内容:
  - JS側の seek 処理は `position` が有限かつ0以上かだけを確認し、`target.currentTime = position` を実行しています。
  - `isSeekable`、`seekableStartSeconds`、`seekableEndSeconds`、`durationSeconds` を使った範囲確認がありません。
  - 代入後の実位置が要求位置に一致しない場合も `seek-requested` として扱われ、失敗条件に含まれていません。
  - `MainWindow.SeekToFromIpcOnUiAsync` はこの結果を `SeekControlResult` へ変換するだけで、追加検証を行っていません。
- 発生条件:
  - 通常動画の長さを超える位置へ `seek-to` / `player-seek` する。
  - ライブ配信やDVR範囲外へ `player-seek` する。
  - ブラウザ側が `currentTime` をクランプする、またはシークを受け付けない。
- 想定される影響:
  - Control側では成功扱いになるが、実際には要求位置へ移動していない。
  - ライブや広告中などで不正なシーク結果が返る。
  - お気に入り再生は別途検証していますが、IPCの任意シークでは誤成功になります。
- 修正案:
  - JS側で seek 前に `isSeekable` と seekable 範囲、通常動画では `duration` を検証する。
  - seek 後に短い確認ループまたは状態再取得で `currentTime` が許容誤差内に入った場合だけ成功にする。
  - `seek-requested`、`volume-mismatch` と同様の中間状態を成功にしないレスポンス規約へ整理する。
- 修正要否:
  - 必須修正です。

### 3. High: 動画切替後の希望音量/ミュート再適用が即時実行されない

- 対象ファイル: `MainWindow.xaml.cs`
- 対象行: 1696-1724
- 関連ファイル: `Services/UnifiedPlayerControlService.cs`
- 関連行: 452-475, 515-520, 523-545
- 問題内容:
  - NavigationCompleted 後、希望音量または希望ミュートがある場合に `ApplyUnifiedPlayerControlAfterNavigationAsync` が呼ばれます。
  - しかし実行しているコマンドは `player-get-state` です。
  - JS側では `get-state` 時に `syncDesiredFromHost()` と `ensureObserver()` は行いますが、現在の `target` へ `applyDesired()` を即時実行していません。
  - `applyDesired()` が直接呼ばれるのは主に `set-control-policy` と `play` の前であり、`get-state` ではイベント待ちになります。
- 発生条件:
  - Control側で希望音量を設定した後にYouTube内で動画が切り替わる。
  - NavigationCompleted 後350msの時点で `loadedmetadata` / `canplay` などがすでに発火済みで、以後 MutationObserver やメディアイベントが発生しない。
- 想定される影響:
  - 新しい動画で希望音量が再適用されず、YouTube側の既定音量や前回ページ状態のまま再生される。
  - ミュートは旧 `MutePersistenceService` が有効な場合は補完されますが、音量は旧 `AudioPersistenceService` が現在呼ばれていないため漏れやすいです。
  - 「Control側の希望音量とミュート状態を維持する」という今回の目的に反します。
- 修正案:
  - NavigationCompleted 後の再適用用に `player-get-state` ではなく、明示的な `reapply-desired-state` 相当の操作を追加する。
  - または `get-state` でも希望状態が渡されている場合は、snapshot前に一度 `applyDesired("navigation-completed")` を実行する。
  - 旧 `AudioPersistenceService` を残す場合は、呼び出し経路を明確にする。統合サービスへ一本化する場合は未使用メソッドを整理する。
- 修正要否:
  - 必須修正です。

### 4. Medium: `play()` の Promise 拒否がレスポンスに反映されない

- 対象ファイル: `Services/UnifiedPlayerControlService.cs`
- 対象行: 543-549, 596-609
- 問題内容:
  - `target.play()` の戻り Promise に `catch` は付けていますが、IIFE は `async` ではなく、Promise の完了を待たずにレスポンスを返します。
  - `catch` 内で `state.lastPlayError` に保存しても、今回の `after` レスポンスには反映されません。
  - `operationResult` は `play-requested` または `playing` になり、失敗条件に含まれません。
- 発生条件:
  - ブラウザの自動再生制限、サイト側制限、広告中、プレイヤー未準備などで `play()` が reject される。
  - お気に入りの自動再生ONでシーク後に再生開始する。
  - Control側から `player-play` を送る。
- 想定される影響:
  - IPCでは成功なのに再生が始まらない。
  - お気に入り再生完了ログが成功になっても、実際は停止したままになる。
- 修正案:
  - JS IIFEを `async () => { ... }` にして `await target.play()` する。
  - reject時は `PLAY_REJECTED` など既存のエラーコードを設定し、`after.success = false` で返す。
  - 必要であれば短いタイムアウトを設け、`paused` が解除されたことを確認する。
- 修正要否:
  - 必須に近い修正です。少なくともIPCレスポンスの成功条件から `play-requested` を外すべきです。

### 5. Medium: お気に入り再生要求のキャンセル後に古い処理が残る余地がある

- 対象ファイル: `MainWindow.xaml.cs`
- 対象行: 2319-2389, 2418-2445, 2469-2485
- 関連ファイル: `Services/UnifiedPlayerControlService.cs`
- 関連行: 96-104
- 問題内容:
  - `ApplyPendingFavoritePlaybackAsync` はループ冒頭と検証待機中に `IsCurrentFavoritePlaybackRequest` を確認しています。
  - しかし `ExecuteUnifiedPlayerControlOnUiAsync` の await 後、ミュート適用、ループ適用、シーク、再生/一時停止の各段階の直前には最新リクエスト確認がありません。
  - `UnifiedPlayerControlService.ExecuteAsync` は `OperationCanceledException` も通常の `Exception` として捕捉し、例外を投げずに失敗結果を返します。
  - そのため、キャンセル済みリクエストが失敗結果を受け取った後に、古いリクエストとしてエラー表示へ進む余地があります。`ApplyFavoriteLoopAsync` は CancellationToken を受け取らないため、キャンセル後も旧リクエストのループ設定を適用し得ます。
- 発生条件:
  - お気に入りボタンを素早く連続押下する。
  - 先行リクエストが `ExecuteScriptAsync` 実行中にキャンセルされる。
  - 旧リクエストの await が新リクエスト作成後に戻る。
- 想定される影響:
  - 最新のお気に入り操作中に、古いリクエスト由来の警告ダイアログが表示される。
  - 古いボタンのループ設定だけが後から残る。
  - 「最新押下を必ず優先」という受け入れ条件が競合時に破れる。
- 修正案:
  - 各 await の直後、かつミュート/ループ/シーク/再生の直前に `IsCurrentFavoritePlaybackRequest(request)` と `cancellationToken.ThrowIfCancellationRequested()` を入れる。
  - `UnifiedPlayerControlService.ExecuteAsync` では `OperationCanceledException` を握りつぶさず再throwし、呼び出し側でキャンセルとして扱う。
  - `ApplyFavoriteLoopAsync` に CancellationToken と request 確認を渡す。
- 修正要否:
  - 修正推奨です。連続押下を重視する今回のチケットでは優先度高めです。

### 6. Low: 同一YouTube動画ID判定が Shorts / live / youtube-nocookie 形式を扱えない

- 対象ファイル: `MainWindow.xaml.cs`
- 対象行: 2558-2591
- 問題内容:
  - 同一動画ID判定は `youtu.be/{id}`、`youtube.com/watch?v=...`、`youtube.com/embed/{id}` のみ対応しています。
  - `youtube.com/shorts/{id}`、`youtube.com/live/{id}`、`www.youtube-nocookie.com/embed/{id}` は動画IDを抽出できません。
  - `IsYouTubeUrl` では `www.youtube-nocookie.com` をYouTube扱いしているため、判定基準に不整合があります。
- 発生条件:
  - Shorts URLや live URL、nocookie embed URLをお気に入りへ登録する。
  - 同じ動画を別URL形式で表示中にお気に入りを押す。
- 想定される影響:
  - 同一動画でも `sameVideo` にならず、ページ再読み込みが発生する。
  - 「URL形式違いでも同一動画として扱う」という確認ポイントを満たしきれない。
- 修正案:
  - `/shorts/{id}`、`/live/{id}`、`youtube-nocookie.com/embed/{id}` を `TryGetYouTubeVideoId` に追加する。
  - 可能なら `FavoritePlaybackUrlService` 側の動画ID抽出と共通化し、対応形式の差をなくす。
- 修正要否:
  - 任意改善ですが、YouTubeの主要URL形式として対応推奨です。

## 問題が見つからなかった重点確認項目

- Debugビルド、Releaseビルドはいずれも成功しました。
- `UnifiedPlayerControlService` の WebView2戻り値デコードは、JSON文字列・JSONオブジェクト・空オブジェクトを区別する方向へ修正されています。
- お気に入りの `00:00:00` は「何もしない」ではなく、seek対象として扱われています。
- スタート位置入力の `HH:mm:ss` と数字のみ右詰め変換は、既存チケットの仕様例（`30` -> `00:00:30`, `13000` -> `01:30:00`）に合っています。
- 旧お気に入りJSONに削除済みプロパティが残っていても、`System.Text.Json` の既定動作で未知プロパティは無視され、`startPositionSeconds` 未設定時は `0` として扱われます。
- 同一動画IDの直接シークは、`watch` / `youtu.be` / `embed` 形式では実装されています。

## 修正優先順位

1. `player-set-volume` / `player-set-muted` の必須パラメータ検証とJS側防御を追加する。
2. `player-seek` / `seek-to` の seekable 範囲、動画長、実位置確認を追加する。
3. NavigationCompleted 後の希望音量/ミュート再適用を、状態取得ではなく実適用として実行する。
4. `play()` Promise を await し、reject をIPC失敗として返す。
5. お気に入り連続押下時のキャンセル伝播と、各 await 後の最新リクエスト確認を強化する。
6. YouTube動画ID抽出の対応URL形式を増やし、抽出処理を共通化する。

## 今後の推奨対応

- IPCコマンドごとに「必須パラメータ」「成功条件」「中間状態を成功に含めるか」を表にして、`IpcCommandHandler` と JS 側で同じ規約にすることを推奨します。
- WebView2 JS 操作は、`requested` と `completed` を分け、Controlへ返すレスポンスは原則 `completed` のみ成功にすると状態不整合を減らせます。
- お気に入り再生処理は、`FavoritePlaybackRequest` と `CancellationToken` を各サブ操作に渡し、キャンセル時はUI警告を出さず静かに終了する形へ寄せると連続押下に強くなります。
- `AudioPersistenceService`、`MutePersistenceService`、`UnifiedPlayerControlService` の役割を整理し、最終的に同じメディア要素へ複数のObserverが競合しない構成へ統合することを推奨します。
